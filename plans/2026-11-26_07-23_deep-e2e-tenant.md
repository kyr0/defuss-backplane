# Deep e2e suites in the `_e2e_test_<app>` tenants

The human asked for this on 2026-11-26: one suite tests the real behavior of every subsystem through MCP and through RPC, in the tenant `_e2e_test_backplane`. linear-clone gets the same kind of suite in its own tenant, `_e2e_test_linear-clone`. Every feature the daemon exposes gets a test. That includes streaming video from vfs and uploading and downloading a 512 MB file.

## Decisions (human, 2026-11-26)

- One suite, two targets. `make e2e` runs it against the throwaway daemon of the packed-consumer test, in the gate and in CI. `make e2e-live` runs it against the running daemon, connecting with `.env` and `.mcp.json`.
- On a running daemon, each run gets fresh bucket names (a run ID) and deletes its cache keys, documents and files. Log records and terminated schedules stay in `_e2e_test_backplane`, because the backplane has no API to delete them.
- Video: a WebM fixture under `input/`, which ffmpeg can regenerate. Playwright's Chromium has no H.264. The suite checks the range semantics of `/files` byte for byte. Then Chromium plays the video through an app-style proxy, the way the README describes the browser path, and seeks; the seeks must produce 206 responses.
- The 512 MB transfer runs in every `make e2e`. Its content is random bytes, checked by SHA-256. A bound on the daemon's memory proves streaming, and the suite checks free disk first.

## Evidence

- The tenant name is `_e2e_test_<app>`: `_e2e_test_backplane` for the backplane suite and `_e2e_test_linear-clone` for linear-clone's. linear-clone keeps its data in the backplane tenant named by `WORKSPACE`. Its live run therefore starts its own instance of the built app with `WORKSPACE=_e2e_test_linear-clone` against the running backplane, and the instance a person uses keeps its workspace untouched.

- VERIFIED: tenant names may start with `_`; only app names are reserved (`src/scope.ts:appComponent`).
- VERIFIED: the daemon serves 33 RPC methods: 29 MCP tools plus `claim`, `renew`, `complete` and `fail` (the running daemon's `/rpc/schema`). `/vfs/object` serves PUT and GET with conditional headers. `/files/<app>/<tenant>/<bucket>/<key>` serves GET and HEAD with ranges, `If-Range`, the 304 and 412 answers, a Content-Type by extension and `nosniff` (README, `src/transfer.ts`, `src/ranges.ts`).
- VERIFIED: ffmpeg and ffprobe are installed, and the data volume has 170 GB free. The root has no Playwright; linear-clone pins playwright-core 1.65.1, whose Chromium is already in the local cache.

## Design

- `scripts/deep/` holds one module per subsystem (`cache`, `db`, `vfs`, `logs`, `scheduler`, `http`) and a runner (`run.ts`). Each scenario runs twice, through an RPC driver and through an MCP driver with the same interface, and asserts the documented behavior both times. Where only one transport exists, it runs once: streaming files, `/files`, worker leases and probes over HTTP or RPC, and the 1 MiB limits as refusals over MCP.
- Coverage guard: the runner records every RPC method and every MCP tool argument it used. It fails unless every method in `/rpc/schema`, every listed tool and every property of every tool's input schema ran at least once. So a new feature without a test fails the gate.
- Targets: `make e2e` copies the suite into the packed consumer and runs it with that daemon's `mcp.json`. `make e2e-live` runs it from the source tree with `node --env-file=.env`, using the root's `.mcp.json`. The runner takes the MCP config path and the daemon's pid as flags; the pid is for the memory bound.
- The report goes to `output/deep.json`, listing scenarios, transports, durations, the throughput of the 512 MB transfer and the memory growth.

## Results (2026-11-26)

- VERIFIED: backplane `make e2e` ran the deep suite once in its Node.js phase: 97 steps, 0 failed, no unused RPC method, MCP tool or tool argument (output/deep.json). The 512 MiB upload took 9.1 s, each download under 0.7 s, and the daemon's resident memory grew by at most 6 MiB.
- VERIFIED: backplane `make e2e-live` against the daemon started before this work failed exactly the two defects fixed here: an oversized `/rpc` body broke the connection (EPIPE), and `backplane_scheduler_errors_total` was absent. `make restart` loads the fixes.
- VERIFIED: defects found and fixed with regression tests. `src/server.ts:bounded` now reads an oversized body to its end before the 413; the probe saw 4 of 10 clients sending 4 MiB fail with EPIPE before, and 0 of 50 across five sizes after. `src/telemetry.ts` exports the scheduler error counter at 0 (tests/o11y.test.ts). linear-clone `src/server/jobs.ts:upsertSchedules` created a removed or terminated schedule again under its reserved ID, so the app could not start after that; now it creates a successor under the job's `ref` (tests/jobs.test.ts).
- VERIFIED: an explicit log `id` must be a UUID; the README says so now.
- VERIFIED: linear-clone `make e2e` passed 51 checks, the deep suite's 27 among them, and two consecutive deep runs against one backplane passed. `make e2e-live` passed 27 of 27 against the running backplane, and the app `make start` runs kept serving its workspace.
